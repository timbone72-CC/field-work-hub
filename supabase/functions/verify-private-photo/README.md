# Trusted private photo verifier

Source checkpoint only. Not deployed, no bucket provisioned, no real Storage/TUS proof yet.

`POST` accepts only `action_id`, `photo_id`, `transfer_version` UUIDs and the original capturing user's bearer JWT. Trusted Auth validates that exact JWT; the service-only target and confirmation revalidate its exact session against the current work or fixed accepted-Finish recovery predicate. No user-supplied URL, bucket, key, owner, session, size or hash is accepted. Configuration uses the existing server-only Supabase environment credentials; these never reach the dashboard/Android response or logs. Requests fetch only that configured HTTPS Supabase origin and reject redirects.

The worker gets the exact private catalog identity, streams one registered derivative into bounded memory, checks observed byte count, JPEG start/end framing and actual SHA-256, then calls the retained guarded receipt engine. Framing is not a full JPEG decode. Storage metadata or upload HTTP success cannot create a receipt. Confirmation serializes with current access/session changes and current catalog ID/version/owner/path before the immutable ledger/state transaction. Reads happen outside SQL locks. At most two reads per isolate, 32 MiB per derivative and a 45-second total deadline; no distributed throughput guarantee. Oversize images remain WAITING with `VERIFICATION_SIZE_LIMIT`, preserving local and remote content.

`200 RECEIVED` returns only photo/transfer/receipt UUIDs and state. A previously recorded receipt is historical verification proof returned after current original-owner authorization; it does not promise current object availability. Gallery/recovery/provider reads must separately prove bytes remain available. Transient network/408/429/5xx/deadline failures preserve WAITING/previous facts, use safe retry and preserve valid upstream Retry-After. Missing/conflicting/mismatched content needs exact-key reconciliation, never overwrite/delete or a new identity. A lost confirmation response can retry and recover the stored receipt without another download. Client Send, final delivery and cleanup are independent.

Existing CI tests execute the same handler with controlled fetch/stream fixtures and the runtime wiring, plus catalog/RLS/authority gates and actual two-connection PostgreSQL races. These are not hosted Edge or real object evidence.

Before activation, complete governed migration/bucket/auth/grant/policy deployment parity, actual private object download and catalog-version observations, interrupted TUS/exact-key reconciliation, valid current and expired sessions, wrong-role/owner/path operations, supported image-size/resource measurements and phone/laptop recovery checks. Confirm gateway JWT configuration against the actual signing setup; this handler's Auth/session validation remains mandatory regardless of gateway configuration. No dashboard or Android integration is switched on by adding this source.
