## Business outcome and finite release milestones

**Product finish line:** a contractor receives and acknowledges assigned work, captures/finishes offline without evidence loss, and an authorized office user can review/correct, approve, intentionally Send, track actual client delivery and retain or safely clean originals according to verified receipts. Authorized staff and second devices work without special developer intervention. An outside pilot needs separate controlled identity, storage/retention, update and backup operations.

**The five fixed AC identifiers are release/acceptance milestones, not five tests and not the entire backlog.** A feature may need implementation and controlled activation before it can be accepted. The approved roadmap and mandatory protection checks remain the actual completion contract. A defect is repaired inside its feature/milestone, not via another arbitrary acceptance gate. Adding a sixth milestone requires an operator-approved material change that an existing milestone cannot cover.

## Mandatory build-to-business workflow (every runtime PR and handoff)

**Work lane is exactly one of: FINISH, ACTIVATE, ACCEPT or RELEASE.** It is a stage of delivering the same product feature, **not** a new phase or another authorization gate. SAFETY is a scoped emergency correction; GOVERNANCE is documentation/process work. The default priority order is a real blocker to safe operation (F04/AC1), then F05/AC2, then remaining approved F01/F03/F06/F07/F08/AC3. If an external blocker stops AC1, advance independent AC3 feature implementation instead of adding a fresh audit or invented TEST fixture.

1. **Identify the business outcome:** read governed \`main\`, active work and the existing implementation record; identify the numbered milestone and FWH-F ID, exact current state (WORKING / BUILT_INACTIVE / PARTIAL / NOT_BUILT / DEFERRED), accepted evidence and **smallest remaining business functionality**. Work only from the approved roadmap; no phase drift, new owner, duplicate worker or repeated design approval.
2. **FINISH:** implement the largest coherent unfinished approved behavior with focused tests. Source-implemented but merely OFF is **ACTIVATE** after the existing safe readiness steps, not a reason to rewrite code. A feature is not “done” because tests compile or a PR merges.
3. **ACTIVATE:** verify exact tested version, authenticated external identities, approved migrations/config, rollback, protected originals/receipts, tenant/role authority and prior gates; change only the explicitly authorized TEST/production flags. **Never confuse planning approval, merge approval, and a live provider/destructive activation authorization.** If provider identity or uncertainty cannot be proven, stop that specific mutation and continue independent work.
4. **ACCEPT:** apply accepted earlier automated/phone/Google evidence directly. Select only the smallest *previously unproven* real-device/provider/end-to-end boundary for the newly finished/activated feature. Combine compatible observations into one user-facing workflow. Focused CI while developing and one final required exact-head suite are standard code quality checks—not new physical acceptance rounds. Record PASS/BLOCKED/FAIL honestly; a defect triggers a narrow fix within the **same feature and milestone**.
5. **RELEASE:** only after the milestone's actual business exit criteria, relevant Phase 7/8 boundaries, environment/live parity and existing Level 3 gates pass, approve the controlled pilot scope and updater/rollback. Record the candidate, enablement and recovery operations. Do not activate optional functionality by implication.
6. **Handoff and next action:** update the **single existing** \`docs/PHASE_5_6_IMPLEMENTATION_RECORD_2026-10-06.md\` (archive before 24 KiB) or successor governed implementation record, with **feature ID, lane, from/to status, precise work delivered, authoritative SHA, external switch state, accepted evidence, blocked dependency and next feature action**. No second implementation ledger or repeated general audit.

**Required compact report:** \`FWH v1: AC1–AC5 statuses | Current feature: FWH-F## | Lane: FINISH/ACTIVATE/ACCEPT/RELEASE | Completed business behavior | Exact next action\`. “Five milestones” is never a count of tests remaining, and a CI rerun or documentation PR is not counted as feature progress.

## Enforceable no-drift, no-repeat and scope rules

- Every new runtime/CI PR declares **Acceptance gate (AC1–AC5)**, **Feature ID (F01–F08 or tightly justified PLATFORM)**, **Work lane (FINISH/ACTIVATE/ACCEPT/RELEASE)**, **Feature state before/after**, and **Work outcome** (what usable behavior changes). Runtime PRs may not silently substitute tests, refactors or scaffolding for the feature outcome; the handoff records what actually works. An emergency **SAFETY** lane needs a real linked incident.
- Every runtime/CI PR also declares **New physical/provider evidence: NONE** or \`FWH-AC#: <specific previously unaccepted reality boundary>\`. Repeating accepted physical tests requires the actual changed identity/boundary and why its prior evidence is invalid in the PR record; a new session, release number, merge or anxiety is not such a reason.
- **ACTIVATE** PRs identify the specific environment/switch and safe rollback boundary. **ACCEPT** or **RELEASE** PRs identify exact existing new evidence references; \`CI green\` alone cannot prove Google/provider/Android behavior. The checks enforce *declarations*, not truth or approval.
- No material approved Phase 5/6 feature is silently deferred, deleted from the register, or pronounced WORKING without evidence. Optional features may be left OFF for v1 only under a recorded operator product-scope decision consistent with the governing plan. A new business feature requires normal roadmap scope approval; not a spontaneous “test improvement”.
- Existing accepted results survive future PRs unless the exact protected boundary changed. Failure blocks the smallest affected feature, not independent safe work. Documentation changes or checker maintenance do not consume a milestone or physical test.
- Source release/TEST switches, legacy permit, preserved private originals and FPP separation remain protected. This proposal grants **no** merge/SQL/worker/Google/cleanup/APK/production authority.
- The existing required GitHub \`governance\` check will validate the declared milestone/feature/lane/status/outcome and special activation/acceptance references once the proposal is merged. Repo ruleset is active and already requires this check; GitHub cannot validate real device/provider truth or replace Level 3 operator approval.
