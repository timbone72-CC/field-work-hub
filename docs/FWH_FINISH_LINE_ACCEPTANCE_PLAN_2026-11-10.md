## The straight-line operating workflow (every PR and session)

1. **Anchor:** read latest `main`, relevant active PR and this five-gate table; name the **one** gate being advanced. For already accepted work, preserve its original evidence and do not restage it. First pick AC1 until its exit criterion is satisfied or genuinely blocked.
2. **Build:** select the largest safe coherent change for that gate under the existing owner. No parallel worker, redundant phase plan, new test package, return to previously accepted photo capture, or speculative feature detour. A focused fix stays under the same gate.
3. **Verify proportionately:** focused automated tests of changed behavior while building, **one** full exact-head CI suite when required before the runtime merge, and **one combined physical/provider acceptance** for the new behavior software cannot prove. The usual CI checks on successive PRs are build validation, **not additional physical acceptance rounds**. Existing accepted evidence is inherited until its affected boundary actually changes.
4. **Decide at a genuine boundary:** only a new material risk, contradiction, required Level 3 pre-merge authorization, live-config change, safe provider-operation approval, or physical uncertainty can stop the **affected** work. Bundle the known TEST activation actions into one intelligible authorization request when technically safe; never split one unchanged approval into individual photo, RPC, folder, or step permissions.
5. **Close or contain:** record `PASS`, `BLOCKED` or `FAIL` with exact evidence, runtime/DB/worker switches, rollback and the next remaining gate in the **existing** implementation record. A FAIL gets one narrowly scoped repair and relevant verification; a BLOCKED item keeps its ID and preserved state. Do not count a merged documentation PR, a fresh audit, an unrelated CI rerun or a plan amendment as an acceptance advance.

**Every status report** should begin `Finish-line gates: X/5 PASS | Current gate: AC# | Exact next action: ...`. State any genuine uncertainty once, with its affected boundary. Never state an invented number of tests to go.

## Explicit anti-drift and no-repeat rules

- A new runtime PR must identify one of `FWH-AC1` … `FWH-AC5` in its existing governance metadata. Emergency safety corrections may use `FWH-SAFETY` with a linked incident and a narrow description. Documentary-only PRs may use `N/A`. Neither is a new acceptance gate.
- A runtime PR must declare `New physical/provider evidence: NONE` **or** `FWH-AC#: <specific never-accepted boundary>`. Any proposal to repeat accepted physical tests requires an explicit changed-boundary explanation in the PR and acceptance record; a new PR, session, rebuild, CI PASS or nervousness is insufficient.
- No later gate can silently supersede an accepted earlier outcome. Document changes to the defined product/authority/retention requirements require normal existing change-control approval; no auto-merges or relaxed protection.
- No production rollout, spontaneous activation of optional Web Push/email, destructive cleanup, Team/FPP data crossover, or photo/Drive mutation is authorized by this plan.
- The existing GitHub **required `governance` status check** can reject runtime PRs missing those declarations once the associated workflow change is merged. GitHub can validate a PR's declared gate and the permitted form of evidence, but cannot know whether a test was physically performed or establish real provider truth. Humans enforce the evidence itself. Verify the repository ruleset continues to require `governance`.
