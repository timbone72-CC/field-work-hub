## Business outcome and finite release milestones

**Product finish line:** a contractor receives and acknowledges assigned work, captures/finishes offline without evidence loss, and an authorized office user can review/correct, approve, intentionally Send, track actual client delivery and retain or safely clean originals according to verified receipts. Authorized staff and second devices work without special developer intervention. An outside pilot needs separate controlled identity, storage/retention, update and backup operations.

**The five fixed AC identifiers are release/acceptance milestones, not five tests and not the entire backlog.** A feature may need implementation and controlled activation before it can be accepted. The approved roadmap and mandatory protection checks remain the actual completion contract. A defect is repaired inside its feature/milestone, not via another arbitrary acceptance gate. Adding a sixth milestone requires an operator-approved material change that an existing milestone cannot cover.

## Build-to-business workflow — no extra test stages

**FINISH → ACTIVATE → ACCEPT → RELEASE** are statuses of one business capability, not additional phases, test campaigns or permissions. The default approved priority is FWH-F04/AC1 normal delivery, then FWH-F05/AC2 cleanup, with independent FWH-F01/F03/F06/F07/F08/AC3 work continuing if the provider is genuinely blocked. All eight business capability statuses remain in the feature register above and the single authoritative implementation record.

1. **FINISH:** verify the current feature and credited prior evidence, then implement the largest coherent missing approved business behavior. Reuse working code; if the behavior is built but OFF, take it to the existing activation boundary instead of rebuilding or inventing a fixture. Focused tests during development, one exact-final-head required CI suite for runtime changes.
2. **ACTIVATE:** identify exact tested source, environment/switch, protected roles/destination/originals, rollback and confirmed operator authority. Set only approved switches for that specific environment; no planning or PR metadata automatically authorizes a DB/Edge/Google/Android/cleanup/production action.
3. **ACCEPT:** use the accepted evidence register without retesting unchanged phone, browser or provider guarantees. Apply the existing [TESTING_CONTRACT.md](../TESTING_CONTRACT.md#accepted-evidence-and-retest-decision) COVERED/NEW/INVALIDATED/BLOCKED rule. For genuinely NEW or INVALIDATED provider/device behavior, perform only the smallest combined new reality observation. Keep PASS/BLOCKED/FAIL accurate.
4. **RELEASE:** once the existing approved milestone exit criteria and Phase 7/8 controls are actually satisfied, use the standard bounded pilot, updater, recovery and rollback policies. No full release merely because two hardcoded TEST pins work.
5. **Handoff:** update the one authoritative `docs/PHASE_5_6_IMPLEMENTATION_RECORD_2026-10-06.md` (archive before its 24 KiB hard limit) with feature, state, delivered behavior, authoritative SHA, external switch, existing/new evidence, blocker and exact next action. This is not a new ledger or review PR requirement.

**Only four compact additional PR fields for runtime/CI changes:** `Feature / milestone` (for example `FWH-F04 / FWH-AC1`), `Work lane` (`FINISH`, `ACTIVATE`, `ACCEPT`, `RELEASE` or scoped `SAFETY`), `Business outcome` (the usable feature improvement; name affected features for `FWH-PLATFORM`), and `New physical/provider evidence` (`NONE` or `FWH-AC#: specific previously unproven reality boundary`). Documentation-only governance work does **not** require this metadata. The existing governance fields already cover scope, protected behavior, external systems, rollback, verification and Level-3 approval. ACTIVATE records its actual switch/rollback there; ACCEPT/RELEASE cite real evidence in the existing Evidence / Remaining Gates section; a SAFETY outcome links the real incident issue.

**The checker validates only these declarations, not their truth.** It does not invent tests, require feature state before/after on every PR, create another acceptance checklist, or grant activation/merge approval. A completed source/CI step is not automatically a WORKING feature. The five AC milestones are product outcomes, not a promised count of tests remaining.

## No-repeat and bounded-scope enforcement

- **Accepted reality remains accepted.** A new commit, PR, version, documentation edit, phase label or anxiety is not a reason to request another camera/offline/Drive screenshot. Repeat an observation only when exact behavior/authority/data identity changed or contradicting evidence makes its former proof insufficient; record the changed boundary and reuse the rest.
- **A NEW boundary is not a retry of the entire workflow.** Stage the smallest necessary genuine Google/Android/provider/user-facing observation, preferably within normal approved operation; combine compatible checks. Actual uncertain remote state still stops only the affected unsafe mutation, preserving original IDs/evidence.
- The long Phase 7 scenario catalog is a **coverage inventory and everyday pilot reliability guide**, not a command to rerun every prior isolated test. Previously accepted Phase 2–4, one-package delivery, two-Admin conflict and v42 data-preservation evidence all count. The actual integrated pilot must still be genuinely observed.
- An independent approved feature may progress when another external provider boundary is blocked; a failure may not silently relax cross-tenant authorization, cleanup eligibility, immutable remote identity, accepted Finish, or previously required recovery rules.
- No approved Phase 5/6 required feature may be silently removed or called WORKING without appropriate evidence. Optional v1 deferrals need a real product decision, not a documentation workaround.
- Keep all original FPP/HELD evidence, TEST/production separation, exact Level-3 pre-merge approval and separate provider/destructive/deployment permissions. This PR changes governance only.
